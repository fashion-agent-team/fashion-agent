# Feature Specification: 계정과 회원정보

**Feature Branch**: `(브랜치 없음, docs 정리)`

**Created**: 2026-11-04

**Status**: Draft

**Input**: User description: "애플·구글로 로그인하고, 음성 온보딩에서 회원정보(이름·생년월일·성별·직업·키·몸무게·에이전트 이름)를 건너뛰기 가능하게 받는다. 일정 알림과 가족 답장 알림을 받을 폰을 등록하고, 로그인을 30일 유지한다."

**주인 서비스**: gateway (스키마 `account`) · 근거: `docs/contracts/README.md` 3·7절, `openapi.yaml` auth·profile

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 애플·구글 계정으로 로그인 (Priority: P1)

시각장애인 사용자가 앱을 처음 열면 VoiceOver/TalkBack으로 애플 또는 구글 로그인을 눌러 들어간다. 다시 열 때는 로그인 화면 없이 바로 대기 화면으로 간다.

**Why this priority**: 계정이 없으면 일정·옷장·가족 확인 등 사용자별 데이터를 하나도 저장할 수 없다.

**Independent Test**: 새 기기에서 구글 로그인 → 같은 구글 계정으로 다른 기기 로그인 시 같은 사용자로 인식되는지 확인.

**Acceptance Scenarios**:

1. **Given** 처음 쓰는 사용자, **When** 애플 로그인을 마치면, **Then** 새 계정이 만들어지고 "처음 오셨어요"를 알리는 신호(새 사용자 여부)를 받아 음성 온보딩이 시작된다.
2. **Given** 이미 가입한 사용자, **When** 같은 계정으로 다시 로그인하면, **Then** 새 계정을 만들지 않고 기존 데이터(일정·옷장)를 그대로 쓴다.
3. **Given** 개발 환경, **When** 기기 id로 개발용 로그인을 하면, **Then** 개발용 계정으로 들어가며, 발표 빌드에서는 이 방법이 막혀 있다.

---

### User Story 2 - 음성 온보딩으로 회원정보 입력 (Priority: P2)

에이전트가 "이름을 알려 주세요"처럼 하나씩 묻고, 사용자는 말로 답하거나 "건너뛸게"라고 한다. 마지막에 에이전트 이름을 정하면 온보딩이 끝난다.

**Why this priority**: 직업·체형 정보가 있으면 추천이 나아지지만, 없어도 핵심 기능(옷 추천)은 돌아간다.

**Independent Test**: 모든 항목을 건너뛰어도 저장이 되고, 다시 조회하면 빈 값으로 돌아오는지 확인.

**Acceptance Scenarios**:

1. **Given** 온보딩 중, **When** 키만 말하고 나머지를 건너뛰면, **Then** 키만 저장되고 나머지는 비어 있다.
2. **Given** 에이전트 이름이 비어 있는 사용자, **When** 앱을 열면, **Then** 온보딩을 다시 안내한다(에이전트 이름이 있으면 온보딩 완료로 본다).
3. **Given** 사용자가 "키 300센티"라고 잘못 말함, **When** 저장하면, **Then** 저장을 거부하고 다시 묻는다(키 50~250cm, 몸무게 10~300kg 범위).

---

### User Story 3 - 알림 받을 폰 등록 (Priority: P2)

로그인한 폰을 알림 대상으로 등록해, 일정 당일 아침 알림과 가족 답장 알림을 받는다.

**Why this priority**: 일정(002)과 가족 확인(004)의 알림이 이것에 기대지만, 알림 없이도 각 기능은 동작한다.

**Independent Test**: 폰 두 대에서 같은 계정으로 로그인 → 두 폰 모두 알림 대상에 등록되는지 확인.

**Acceptance Scenarios**:

1. **Given** 한 사람이 폰 두 대를 씀, **When** 둘 다 등록하면, **Then** 두 폰 모두 알림을 받는다.
2. **Given** 가족이 같은 폰에서 다른 계정으로 로그인, **When** 그 폰을 다시 등록하면, **Then** 그 폰의 알림 주인이 새 계정으로 바뀌고 이전 사용자 알림은 그 폰으로 가지 않는다.
3. **Given** 폰 앱을 지워 알림 토큰이 무효가 됨, **When** 알림 전송이 실패하면, **Then** 그 토큰을 지운다.

---

### User Story 4 - 로그인 유지 (Priority: P3)

한 번 로그인하면 30일 동안 다시 로그인하지 않는다. 짧은 출입증이 만료되면 앱이 알아서 새로 받는다.

**Why this priority**: 매번 로그인 화면을 거치는 것은 시각장애인에게 큰 부담이지만, 기능 자체를 막지는 않는다.

**Independent Test**: 출입증 만료 후 요청 → 앱이 갱신 후 한 번 다시 시도해 성공하는지 확인.

**Acceptance Scenarios**:

1. **Given** 출입증(1시간) 만료, **When** 갱신을 요청하면, **Then** 새 출입증과 새 갱신 토큰을 받고 쓴 갱신 토큰은 더 쓸 수 없다.
2. **Given** 로그아웃한 사용자, **When** 예전 갱신 토큰을 쓰면, **Then** 거부된다.

---

### Edge Cases

- 애플 로그인에서 이메일 숨기기를 고른 경우에도 같은 사람으로 인식해야 한다(Firebase 사용자 id 기준).
- 회원정보의 성별·직업은 말로 받으므로 정해진 목록이 아닌 자유 문장일 수 있다.
- 탈퇴 기능은 만들지 않는다 → FR-012.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 애플·구글 로그인 결과(Firebase)를 확인하고, 같은 외부 계정은 항상 같은 사용자로 연결해야 한다.
- **FR-002**: System MUST 개발용 로그인(기기 id)을 개발 환경에서만 허용해야 한다.
- **FR-003**: System MUST 로그인 응답에 새 사용자 여부를 알려 앱이 온보딩을 시작할 수 있게 해야 한다.
- **FR-004**: Users MUST be able to 회원정보 7개 항목(이름, 생년월일, 성별, 직업, 키, 몸무게, 에이전트 이름)을 각각 건너뛸 수 있어야 한다.
- **FR-005**: System MUST 키는 50~250cm, 몸무게는 10~300kg 범위 밖이면 저장을 거부해야 한다.
- **FR-006**: System MUST 사용자 한 명이 알림 받을 폰을 여러 대 등록할 수 있게 하고, 같은 폰은 한 사용자에게만 연결해야 한다.
- **FR-007**: System MUST 무효가 된 알림 토큰은 전송 실패 시 지워야 한다.
- **FR-008**: System MUST 출입증 1시간, 갱신 토큰 30일로 로그인을 유지하고, 갱신할 때마다 갱신 토큰을 새로 바꿔야 한다.
- **FR-009**: System MUST 갱신 토큰 원문을 저장하지 않아야 한다(대조용 값만).
- **FR-010**: System MUST 뒤쪽 서비스로 보내는 사용자 id를 자기가 확인한 값으로 덮어써야 한다.
- **FR-011**: System MUST 다른 서비스(일정 등)가 사용자에게 알림을 보낼 수 있는 내부 통로를 제공해야 한다. 알림 토큰은 이 서비스 밖으로 내보내지 않는다.
- **FR-012**: 탈퇴 기능은 만들지 않는다(2026-11-04 확정). 나중에 만들면 gateway가 각 서비스에 삭제를 요청한다(005 FR-X5).

### Key Entities

- **사용자(users)**: 로그인 방식(애플·구글·개발용), 외부 계정 id 또는 개발 기기 id, 마지막 로그인 시각.
- **회원정보(profiles)**: 사용자당 하나. 7개 항목 모두 비어 있을 수 있음.
- **알림 토큰(push_tokens)**: 사용자 1명 : 폰 여러 대. 폰 종류(iOS·Android), 마지막 확인 시각.
- **갱신 토큰(refresh_tokens)**: 대조용 값, 만료 시각, 폐기 시각.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 스크린리더만으로 처음 로그인부터 온보딩 끝까지 3분 안에 마칠 수 있다.
- **SC-002**: 같은 외부 계정으로 다시 로그인했을 때 계정이 중복으로 생기는 경우가 0건이다.
- **SC-003**: 30일 안에 앱을 다시 열 때 로그인 화면을 다시 보는 경우가 0건이다(로그아웃 제외).
- **SC-004**: 다른 사용자의 일정·옷장을 읽을 수 있는 경로가 0개다.

## Assumptions

- 로그인은 Firebase Authentication을 거친다(Apple 개발자 계정·Firebase 프로젝트 담당은 팀이 정함).
- 알림 통로(FR-011)는 게이트웨이 내부 API `POST /internal/push {userId, title, body}`로 제안하며, 팀 확정 전이다(`docs/infra/DB.md`).
- 데이터 구조는 `docs/infra/DB.md`의 `account` 스키마를 따른다.
