## User Scenarios & Testing *(mandatory)*

### User Story 1 - 가족에게 사진과 질문 보내기 (Priority: P1)

옷을 카메라에 보여 준 뒤 "엄마한테 이 옷 결혼식에 괜찮은지 물어봐 줘"라고 하면, 엄마에게 링크가 든 문자가 간다.

**Why this priority**: AI 판단이 불안할 때 믿을 만한 사람에게 확인받는 것이 이 기능의 전부다.

**Independent Test**: 연락처 하나를 등록하고 요청 → 문자 링크가 열리고 사진과 질문이 보이는지 확인.

**Acceptance Scenarios**:

1. **Given** 등록된 연락처 "엄마"와 10분 안에 찍힌 사진, **When** 요청하면, **Then** 엄마에게 링크 문자가 가고 에이전트는 "엄마에게 보냈어요"라고 말한다.
2. **Given** 등록되지 않은 이름, **When** 요청하면, **Then** 보내지 않고 등록된 사람 목록을 읽어 준다.
3. **Given** 직전 사진이 없음(10분 지남), **When** 요청하면, **Then** 옷을 다시 보여 달라고 안내한다.

---

### User Story 2 - 가족이 웹에서 답하기 (Priority: P1)

가족은 문자 링크를 열어 사진과 질문을 보고 "괜찮아 / 얼룩 있어 / 직접 쓰기"로 답한다. 로그인은 없다.

**Independent Test**: 링크로 답한 뒤 같은 링크를 다시 열면 이미 답했다고 나오는지 확인.

**Acceptance Scenarios**:

1. **Given** 유효한 링크, **When** 답하면, **Then** 답과 답한 시각이 저장되고 사용자에게 "엄마가 답했어요" 알림이 간다.
2. **Given** 만료된 링크, **When** 열면, **Then** 사진을 보여 주지 않고 만료됐다고 알린다.
3. **Given** 이미 답한 링크, **When** 다시 답하면, **Then** 첫 답을 바꾸지 않는다.

---

### User Story 3 - 답 확인하기 (Priority: P2)

"엄마가 뭐래?"라고 물으면 답을 읽어 준다. 아직이면 기다리는 중이라고 말한다.

**Acceptance Scenarios**:

1. **Given** 답이 온 요청, **When** 물으면, **Then** "엄마가 '얼룩 없어, 그림자야'라고 답했어요"라고 읽어 준다.
2. **Given** 답이 아직 없음, **When** 물으면, **Then** 기다리는 중이라고 말한다.
3. **Given** 만료된 요청, **When** 물으면, **Then** 답이 오지 않았다고 말한다.

---

### User Story 4 - 연락처 등록 (Priority: P2)

"엄마 번호 등록해 줘, 010…"처럼 이름·전화번호·관계를 등록한다.

**Acceptance Scenarios**:

1. **Given** 새 번호, **When** 등록하면, **Then** 저장되고 목록에 이름·관계만 보인다(번호는 읽어 주지 않음).
2. **Given** 이미 등록한 번호, **When** 다시 등록하면, **Then** 중복으로 만들지 않는다.

### Edge Cases

- 링크 토큰은 추측할 수 없어야 한다.
- 사진은 요청 후 24시간이 지나면 지운다. 요청 기록(질문·답)은 남는다.
- 문자 발송이 실패하면 요청을 만들지 않고 실패를 알린다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Users MUST be able to 가족·친구를 이름·전화번호·관계로 등록할 수 있어야 한다. 같은 사용자가 같은 번호를 두 번 등록할 수 없다.
- **FR-002**: System MUST 전화번호를 응답·로그·음성 안내에 내보내지 않아야 한다.
- **FR-003**: System MUST 요청마다 추측할 수 없는 링크 토큰을 만들고 문자로 보내야 한다.
- **FR-004**: System MUST 요청 상태를 대기·답함·만료 셋 중 하나로 두고, 답함이면 답과 답한 시각이 꼭 있어야 한다.
- **FR-005**: System MUST 요청 사진을 24시간 뒤 지우고, 그 뒤에는 링크에서 사진을 보여 주지 않아야 한다.
- **FR-006**: System MUST 만료 시각이 지난 대기 요청을 만료로 바꿔야 한다.
- **FR-007**: System MUST 답이 오면 사용자에게 알림을 보내야 한다(계정 서비스의 알림 통로 사용).
- **FR-008**: System MUST 첫 답만 인정하고 바꾸지 않아야 한다.
- **FR-009**: System MUST 사용자 id는 agent가 넣어 준 값만 쓰고, 남의 연락처·요청은 읽을 수 없어야 한다.

### Key Entities

- **연락처(contacts)**: 사용자별. 이름, 전화번호, 관계.
- **확인 요청(requests)**: 연락처 하나 : 요청 여러 개. 질문, 사진 보관 위치, 링크 토큰, 상태, 답, 답한 시각, 만료 시각.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 요청부터 가족 폰에 문자가 도착하기까지 30초 안이다.
- **SC-002**: 가족이 링크를 열어 답하기까지 탭 3번 이내다.
- **SC-003**: 24시간이 지난 사진이 남아 있는 경우가 0건이다.

## Assumptions

- 문자 발송 서비스와 발신 번호는 팀이 정한다(약속 문서 "아직 안 정한 것").
- 링크 주소는 배포 도메인이 정해지면 `https://<도메인>/h/<token>`이 된다.
- 요청 만료는 보낸 뒤 24시간으로 둔다(사진 보관 기간과 같게).
- 데이터 구조는 `docs/infra/DB.md`의 `helper` 스키마를 따른다.
