## User Scenarios & Testing *(mandatory)*

### User Story 1 - 본 옷을 옷장에 기록 (Priority: P1)

옷 추천 2단계에서 카메라에 보여 준 옷들을, 사용자가 "이걸로 할게"라고 하면 옷장에 기록한다. 전에 본 옷이면 새로 만들지 않고 기존 옷에 합친다.

**Why this priority**: 옷장이 쌓여야 "옷장의 남색 셔츠로 바꾸세요" 같은 추천이 가능하다.

**Independent Test**: 같은 셔츠를 다른 날 두 번 보여 주고 마무리 → 옷장에 한 벌만 있고 마지막으로 본 시각이 바뀌는지 확인.

**Acceptance Scenarios**:

1. **Given** 처음 보는 옷, **When** 마무리하면, **Then** 새 옷으로 저장되고 새 옷이라는 표시를 돌려준다.
2. **Given** 전에 저장한 셔츠와 종류·색이 같고 생김새가 매우 비슷함, **When** 마무리하면, **Then** 기존 옷에 합치고 마지막으로 본 시각과 설명만 바꾼다.
3. **Given** 같은 색 다른 종류(셔츠와 니트), **When** 마무리하면, **Then** 합치지 않는다.

---

### User Story 2 - 입은 날 기록 (Priority: P2)

"이걸로 할게"라고 하면 그날 입은 옷을 기록한다. 다음 추천에서 "어제 입은 셔츠는 빼고" 같은 판단에 쓴다.

**Independent Test**: 같은 옷을 같은 날 두 번 기록해도 한 번만 남는지 확인.

**Acceptance Scenarios**:

1. **Given** 옷 두 벌, **When** 오늘 입었다고 기록하면, **Then** 두 건이 기록된다.
2. **Given** 이미 오늘 기록한 옷, **When** 다시 기록하면, **Then** 중복으로 남지 않는다.

---

### User Story 3 - 상황에 맞는 내 옷과 코디 지식 찾기 (Priority: P2)

옷 추천 1단계에서 "오늘 오전 면접, 체감 9도" 같은 상황으로 옷장 후보와 코디 지식을 찾아 GPT에 넘긴다. GPT는 이 안에서만 고른다.

**Why this priority**: 추천을 "내 옷" 기준으로 만들지만, 옷장이 비어도 일반 추천은 나온다.

**Independent Test**: 옷장 10벌로 "면접" 상황을 찾았을 때 격식 있는 옷이 위에 오고, 제외하라고 한 옷은 빠지는지 확인.

**Acceptance Scenarios**:

1. **Given** 옷장에 옷이 있음, **When** 상황·자리 종류·체감 온도로 찾으면, **Then** 비슷한 순서로 최대 정해진 수만큼 후보와 마지막으로 입은 날을 받는다.
2. **Given** 빼고 싶은 옷 목록, **When** 찾으면, **Then** 그 옷은 후보에 없다.
3. **Given** 옷장이 비어 있음, **When** 찾으면, **Then** 빈 후보와 코디 지식만 받고 "비어 있음" 표시를 받는다.

### Edge Cases

- 사진은 저장하지 않는다. 옷장에는 옷의 설명(종류·색·톤·격식·무늬 등)과 그 설명으로 만든 검색용 값만 남는다.
- 같은 옷 판정이 틀려 두 벌이 합쳐지는 것이, 한 벌이 두 개로 남는 것보다 나쁘다(헷갈리면 합치지 않는다).
- 코디 지식은 모든 사용자가 같이 쓰는 문서다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 옷 하나마다 종류·이름·색 이름·색 계열·톤·격식과 전체 설명을 저장해야 한다.
- **FR-002**: System MUST 종류와 색 계열이 같고 생김새 유사도가 기준 이상일 때만 같은 옷으로 합쳐야 한다(헷갈리면 새 옷).
- **FR-003**: System MUST 처음 본 시각과 마지막으로 본 시각을 기록해야 한다.
- **FR-004**: System MUST 입은 날을 옷마다 하루에 한 번만 기록해야 한다.
- **FR-005**: System MUST 상황 문장의 의미로 옷장 후보를 찾고, 자리 종류·체감 온도는 있으면 거르는 조건으로 써야 한다.
- **FR-006**: System MUST 찾을 때 제외 목록과 최대 개수를 지켜야 한다.
- **FR-007**: System MUST 코디 지식 문서 조각을 상황 문장으로 찾아 출처와 함께 돌려줘야 한다.
- **FR-008**: System MUST 사진을 저장하지 않아야 한다.
- **FR-009**: System MUST 사용자 id는 agent가 넣어 준 값만 쓰고, 남의 옷장은 읽을 수 없어야 한다.

### Key Entities

- **옷(garments)**: 사용자별. 종류, 이름, 색, 톤, 격식, 전체 설명, 검색용 값, 처음·마지막으로 본 시각.
- **입은 날(wears)**: 옷 하나 : 여러 날.
- **코디 지식(style_docs)**: 공용. 출처 문서, 조각 번호, 자리 종류, 내용, 검색용 값.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 옷을 5번 보여 줬을 때 옷장에 한 벌로 남는 비율이 90% 이상이다.
- **SC-002**: 서로 다른 옷이 한 벌로 잘못 합쳐지는 경우가 테스트 옷 20벌 기준 0건이다.
- **SC-003**: 옷장 100벌에서 후보를 찾는 데 1초가 넘지 않는다.

## Assumptions

- 검색용 값은 384차원 임베딩(pgvector)으로 시작하며, mcp-closet 담당이 고르는 임베딩 모델에 따라 바뀔 수 있다.
- 같은 옷 유사도 기준값은 테스트 후 정한다.
- 옷 직접 삭제·수정은 발표 범위에서 뺀다.
- 데이터 구조는 `docs/infra/DB.md`의 `closet` 스키마를 따른다.
