# Feature Specification: 일정과 장소 분위기

**Feature Branch**: `(브랜치 없음, docs 정리)`

**Created**: 2026-11-04

**Status**: Draft

**Input**: User description: "사용자가 말로 일정을 등록·확인·삭제한다. 일정 제목과 장소로 그 자리의 분위기(장례·결혼식·격식·업무·운동·평상)를 정해 옷 추천에 쓴다. 일정 당일 아침 8시에 알림을 보낸다."

**주인 서비스**: mcp-schedule (스키마 `schedule`) · 근거: `docs/contracts/mcp-tools.md` mcp-schedule, `README.md` 5·7절

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 말로 일정 등록 (Priority: P1)

"다음 주 토요일 두 시에 더채플앳청담에서 친구 결혼식"이라고 말하면 일정이 저장되고, 에이전트가 날짜·시간·장소를 다시 읽어 준다.

**Why this priority**: 일정이 있어야 옷 추천이 "오늘 결혼식이 있어요"처럼 상황에 맞게 나온다.

**Independent Test**: 일정 하나를 말로 등록하고, 읽어 주는 확인 문장에 날짜·요일·시간·장소·제목이 모두 들어 있는지 확인.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 제목·시간·장소를 말하면, **Then** 일정이 저장되고 "11월 14일 토요일 오후 2시, 더채플앳청담에서 친구 결혼식을 등록했어요"처럼 한 문장으로 확인해 준다.
2. **Given** 장소 없이 "내일 오전 열 시 면접"이라고 말함, **When** 등록하면, **Then** 장소 없이 저장되고 제목으로 분위기를 정한다.
3. **Given** 제목이 비어 있음, **When** 등록하면, **Then** 저장하지 않고 다시 묻는다.

---

### User Story 2 - 일정에 맞는 분위기 정하기 (Priority: P1)

등록할 때 일정의 자리 종류(occasion)를 정해 둔다. 옷 추천은 이 값을 보고 "결혼식이라 흰 상의는 피하세요"처럼 판단한다.

**Why this priority**: 옷 추천 1단계가 바로 이 값을 쓴다. 분위기가 틀리면 추천이 틀린다.

**Independent Test**: 제목 키워드만 있는 일정, 장소만 분명한 일정, 둘 다 없는 일정을 각각 넣고 분위기와 그 근거가 기록되는지 확인.

**Acceptance Scenarios**:

1. **Given** 제목 "장례식", **When** 등록하면, **Then** 분위기는 장례(mourning), 근거는 제목.
2. **Given** 제목 "약속", 장소 "더채플앳청담"(지도 검색 결과 분류 '예식장'), **When** 등록하면, **Then** 분위기는 결혼식(wedding), 근거는 장소.
3. **Given** 제목 "회의", 장소가 등산로, **When** 등록하면, **Then** 제목을 우선해 자리 종류는 업무(business), 근거는 제목(title)으로 저장한다(2026-11-04 확정: 제목 → 장소 → 평상 순서, 앱 PR #15).
4. **Given** 제목·장소로 정할 수 없음, **When** 등록하면, **Then** 분위기는 평상(casual), 근거는 기본값.

---

### User Story 3 - 오늘 일정 확인 (Priority: P1)

"오늘 일정 뭐야?"라고 묻거나 옷 추천을 시작하면 그날 일정을 시간 순서로 받는다.

**Why this priority**: 옷 추천 1단계가 매번 부른다.

**Independent Test**: 같은 날 일정 두 개, 다른 날 일정 하나를 넣고 오늘 조회 시 두 개만 시간 순서로 나오는지 확인.

**Acceptance Scenarios**:

1. **Given** 오늘 일정 두 개, **When** 오늘을 조회하면, **Then** 시작 시간 순서로 두 개를 받는다(장소·장소 분류·분위기 포함).
2. **Given** 오늘 일정 없음, **When** 조회하면, **Then** 빈 목록을 받고 에이전트는 "오늘은 일정이 없어요"라고 말한다.
3. **Given** 다른 사용자의 일정, **When** 조회하면, **Then** 절대 보이지 않는다.

---

### User Story 4 - 일정 당일 아침 알림 (Priority: P2)

일정이 있는 날 아침 8시에 "오늘 오후 2시 친구 결혼식이 있어요. 옷 추천받아 보세요" 알림을 받는다.

**Why this priority**: 일정을 잊지 않게 해 주지만, 알림 없이도 옷 추천은 일정을 읽는다.

**Independent Test**: 오늘 일정이 있는 사용자 한 명, 없는 사용자 한 명으로 8시 작업을 돌려 한 명에게만 한 번 가는지 확인.

**Acceptance Scenarios**:

1. **Given** 오늘 일정이 있는 사용자, **When** 아침 8시가 되면, **Then** 알림이 한 번 가고, 보낸 시각이 기록된다.
2. **Given** 알림 작업이 같은 날 두 번 돌아감, **When** 다시 실행되면, **Then** 이미 보낸 일정은 다시 보내지 않는다.
3. **Given** 오늘 8시 이후에 등록한 오늘 일정, **When** 등록하면, **Then** 아침 알림은 보내지 않는다(등록할 때 이미 확인 문장을 들었으므로).
4. **Given** 알림 전송 실패, **When** 실패하면, **Then** 보낸 것으로 기록하지 않는다.

---

### User Story 5 - 일정 삭제 (Priority: P3)

"토요일 결혼식 지워 줘"라고 하면 그 일정을 지운다.

**Acceptance Scenarios**:

1. **Given** 내 일정, **When** 삭제하면, **Then** 지워지고 "지웠어요"라고 말한다.
2. **Given** 없는 일정이나 남의 일정, **When** 삭제하면, **Then** 지우지 않고 찾을 수 없다고 알린다.

### Edge Cases

- 지도 검색(카카오 로컬)이 실패하거나 느리면 장소 분류 없이 제목으로 정하고 저장은 그대로 한다.
- 같은 이름의 장소가 여러 곳이면 첫 번째 검색 결과를 쓴다.
- 시간은 시간대를 포함해 저장하고, 서울 기준 날짜로 "오늘"을 판단한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Users MUST be able to 제목·시작 시각·장소(선택)로 일정을 등록할 수 있어야 한다. 제목은 비어 있으면 안 된다.
- **FR-002**: System MUST 등록 결과를 날짜·요일·시간·장소·제목이 든 한국어 한 문장으로 돌려줘야 한다.
- **FR-003**: System MUST 장소가 있으면 지도 검색으로 장소 분류를 찾아 함께 저장해야 한다. 못 찾으면 비워 둔다.
- **FR-004**: System MUST 일정마다 자리 종류 6개(장례·결혼식·격식·업무·운동·평상) 중 하나를 정해 저장해야 한다.
- **FR-005**: System MUST 자리 종류를 무엇으로 정했는지(제목·장소·기본값) 함께 기록해야 한다.
- **FR-006**: System MUST 사용자별·날짜별 일정을 시작 시간 순서로 돌려줘야 한다.
- **FR-007**: System MUST 일정 당일 서울 시간 아침 8시에 알림을 사용자당 일정마다 한 번만 보내고, 보낸 시각을 기록해야 한다.
- **FR-008**: System MUST 알림은 [NEEDS CLARIFICATION: 알림 토큰이 계정 서비스에만 있으므로, 계정 서비스의 내부 알림 통로를 부를지(제안), 다른 방법을 쓸지]
- **FR-009**: System MUST 사용자 id는 게이트웨이·agent가 넣어 준 값만 쓰고, 남의 일정은 읽거나 지울 수 없어야 한다.
- **FR-010**: System MUST 지도 검색이 실패해도 일정 등록은 성공해야 한다.

### Key Entities

- **일정(events)**: 제목, 시작 시각, 장소, 지도 장소 id, 장소 분류, 자리 종류, 자리 종류 근거, 알림 보낸 시각.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 말로 일정 하나를 등록하고 확인 문장을 듣기까지 10초 안에 끝난다.
- **SC-002**: 팀이 만든 일정 예시 30개 중 27개 이상(90%)에서 자리 종류가 사람이 정한 답과 같다.
- **SC-003**: 아침 알림이 같은 일정에 두 번 가는 경우가 0건이다.
- **SC-004**: 지도 검색이 꺼져 있어도 일정 등록 성공률이 100%다.

## Assumptions

- 지도 검색은 카카오 로컬 API를 쓴다(키는 배포 비밀 값).
- 반복 일정, 종료 시각, 일정 수정은 발표 범위에서 뺀다(지우고 다시 등록).
- 데이터 구조는 `docs/infra/DB.md`의 `schedule` 스키마를 따른다.
